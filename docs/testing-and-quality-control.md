# Testing And Quality Control

## Подход к контролю качества

В текущем репозитории основной контроль строится не на автоматических тестах, а на проверке полного runtime-контура: инфраструктура, Kafka, ClickHouse, backend API и финальный монитор.

Автоматические unit/integration tests для актуального аналитического модуля в репозитории не найдены. Сборка `./gradlew build` проходит, но задачи `test` для модулей показывают `NO-SOURCE`.

## Контроль по уровням системы

### Инфраструктура

- `Docker Compose` поднимает весь локальный контур.
- Контроль: список сервисов, порты, статусы контейнеров, зависимость Kafka по healthcheck.
- Цель: убедиться, что брокер, ClickHouse, backend, simulator и UI доступны одновременно.

### Kafka и события

- `Kafka UI` показывает наличие топиков `market-requested` и `market-referred`.
- Логи `simulator` подтверждают публикацию тиков, сценариев и промо.
- Логи `analytic` подтверждают прием сообщений listener'ами.
- Цель: проверить, что события реально проходят участок `simulator -> Kafka -> analytic`.

### Backend

- REST API контролируется прямыми HTTP-запросами к `/api/{manufactureId}/...`.
- Код содержит `springdoc-openapi-starter-webmvc-ui` и `@Operation`-аннотации, поэтому OpenAPI/Swagger слой в backend присутствует.
- Логи контроллера и listener'ов позволяют отделить ошибки авторизации, Kafka и WebSocket.

### ClickHouse

- Контроль идет либо через HTTP-запросы к `localhost:8123`, либо через `ch-ui`.
- Проверяется наличие БД `analytic`, таблиц `requested` и `refered`, а также рост количества строк.
- Цель: подтвердить, что данные не только читаются backend-ом, но и реально сохраняются в хранилище.

### API

- Контроль по REST: корректность `X-API-KEY`, формат JSON-ответа, наличие полей `averageRank`, `globalCount`, `referCount`.
- Контроль по WebSocket: успешный handshake, получение `analytics.snapshot`, реакция на ошибки ключа и `manufactureId`.
- Цель: проверить, что backend отдает аналитику в обоих поддерживаемых каналах.

### Монитор

- `analytic-monitor` является финальным пользовательским уровнем контроля.
- Он показывает текущий JSON-ответ и историю метрик на графике.
- Цель: визуально подтвердить, что вся цепочка работает end-to-end, а не только отдельные участки.

## Инструменты контроля

| Инструмент | Подтверждение в проекте | Для чего используется |
| --- | --- | --- |
| `Docker Compose` | `docker-compose.yml` | запуск полного локального контура |
| `Kafka UI` | сервис `kafka-ui` в compose | просмотр топиков и сообщений Kafka |
| `ClickHouse UI` | сервис `ch-ui` в compose | просмотр таблиц и SQL-проверки в ClickHouse |
| `Swagger / OpenAPI` | зависимость `springdoc-openapi-starter-webmvc-ui` и аннотации `@Operation` | ручная проверка REST-контрактов backend-а |
| `Postman` | не подтверждено репозиторием | может использоваться как внешний клиент для ручных HTTP-проверок, но коллекции или скрипты в проекте отсутствуют |
| Собственный монитор | `modules/analytic-monitor` | финальный визуальный контроль всей цепочки |
| Логи | `log.info`, `log.warn`, `log.error` в simulator/backend | диагностика публикации, приема, handshake и ошибок обработки |

## Роль собственного монитора

Собственный монитор не заменяет Kafka UI и ClickHouse UI. Он закрывает последний участок проверки:

- берет результат уже после backend-агрегации;
- показывает текущий ответ в том же виде, в котором его получает клиент;
- строит историю значений по времени;
- позволяет сравнить режимы `REST polling` и `WebSocket`.

Поэтому монитор является средством финального визуального контроля всей цепочки `simulator -> Kafka -> analytic -> ClickHouse -> API / WebSocket -> UI`.

## Что реально можно проверить инструментами

| Уровень | Инструмент | Признак корректной работы |
| --- | --- | --- |
| Контейнеры и порты | `Docker Compose` | сервисы подняты и доступны на ожидаемых портах |
| Kafka transport | `Kafka UI`, логи | топики существуют, сообщения прибывают |
| Сохранение в БД | `ch-ui`, HTTP к ClickHouse | таблицы есть, число строк растет |
| REST API | Swagger / curl / внешний HTTP-клиент | backend возвращает ожидаемый JSON |
| WebSocket | монитор, браузерный WebSocket-клиент | приходят сообщения `analytics.snapshot` |
| End-to-end | собственный монитор | график и JSON обновляются при новых событиях |

## Ограничения

- В репозитории нет `src/test` для актуальных модулей `analytic`, `simulator`, `libs-analytic`.
- Не найдено Testcontainers, mock Kafka или mock ClickHouse.
- Явный URL Swagger UI в проектных настройках не переопределен.
- Использование Postman как фактически примененного инструмента не подтверждается файлами проекта; его можно упоминать только как внешний ручной клиент.
